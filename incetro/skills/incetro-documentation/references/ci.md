# Проверка документации в CI

## Что установлено автоматически

`incetro-ecc init` устанавливает Cursor rule, skill, агент проверки и локальный `check-docs.js` вместе с профилем `core`. Это не создаёт и не меняет GitHub Actions workflow, чтобы не захватывать файлы проекта.

Правило просит агента запускать проверку при завершении содержательных изменений. Нельзя гарантировать выполнение этого шага без соответствующего поведения активного агента.

## Как подключить CI

Скопируй `templates/docs-quality.yml` из установленного skill в `.github/workflows/docs-quality.yml` проекта, проверь список paths и сделай commit. Это явное изменение пользовательского файла. Проверка запускается только после добавления workflow в репозиторий.

```bash
mkdir -p .github/workflows
cp .cursor/skills/incetro-documentation/templates/docs-quality.yml .github/workflows/docs-quality.yml
node .cursor/skills/incetro-documentation/scripts/check-docs.js
```

Workflow проверяет локальные ссылки, Markdown-разделители, некорректные Shields.io стили, символ `—` в обычном тексте. Он не способен автоматически доказать достоверность документации и не блокирует PR без настройки required checks.

Для внешних ссылок можно отдельно добавить Lychee, для форматирования – Prettier или markdownlint. Не подключай скачивание внешних инструментов в критическую цепочку без закрепления версий и проверки безопасности.

## Периодический аудит

Допустим отдельный ежемесячный workflow, который запускает проверки и формирует issue/PR для ревью. Он должен работать с ограниченными разрешениями и не пушить автономные изменения в защищённую ветку. Такой аудит не установлен по умолчанию.

## Проверка перед включением

Сначала приведи существующие docs к стандарту. Если документация исторически использовала горизонтальные разделители или длинное тире, validator честно покажет нарушения. Не маскируй их исключениями в скрипте.
