# Документационная архитектура Incetro

## Главный принцип

Полнота документации означает возможность найти исчерпывающий, актуальный ответ, а не бесконечную длину README. Для каждого факта назначай 1 каноническое место.

## Небольшой проект

Чаще всего достаточно `README.md`. Он отвечает на вопросы: зачем проект, кому нужен, как запустить, как проверить и где исходники важной логики.

## Продукт со сценарием и эксплуатацией

Возможная структура:

```text
README.md
docs/
  product.md
  architecture.md
  development.md
  operations.md
  verification.md
```

Это **пример**, не перечень обязательных файлов. Сохраняй существующие названия документов, ссылки и структуру проекта. Создавай документы только при наличии содержимого.

| Документ | Канонический вопрос | Типичные источники |
| --- | --- | --- |
| `README.md` | Что это и как начать? | проект, manifest, тесты, команды |
| `docs/product.md` | Какие реальные сценарии и ограничения? | handlers, services, спецификация |
| `docs/architecture.md` | Как устроено и как связаны части? | modules, interfaces, schema, migrations |
| `docs/development.md` | Как безопасно разрабатывать и тестировать? | scripts, config examples, tests |
| `docs/operations.md` | Как развернуть, поддерживать и восстановить? | Compose, CI, backup, health |
| `docs/verification.md` | Что проверено, как и с какими ограничениями? | tests, checks, CI logs, acceptance |

## Для сложных проектов

Разделяй документацию по аудиториям и модулям: `docs/api`, `docs/adr`, `docs/development`, `docs/operations`. API-документацию по возможности генерируй из контрактов. Историю решений веди там, где уже ведутся ADR.

## Матрица изменений

| Изменение | Обновить |
| --- | --- |
| Гостевой сценарий / новая функция | product и кратко README, если важно |
| Публичный API / формат данных | API-контракт, ссылки из architecture |
| Новый сервис или схема БД | architecture |
| Новые переменные или команды | development и quickstart |
| Деплой, backup, monitoring | operations |
| Новая гарантия или тест | verification |
| Долговечное решение | существующий ADR |
| Локальный рефакторинг без изменения контрактов | документацию можно не менять |

README должен вести к деталям. Не копируй целые инструкции в несколько мест.

## Ограничения и честность

Разделяй `реализовано`, `проверено`, `планируется` и `не подтверждено`. Не утверждай, что факт проверен CI, если выполнение CI или его результат недоступны. Устаревшее знание убирай или явно отмечай. Не выдавай отсутствие открытой проблемы за доказательство production readiness.
