# Incetro Documentation – visual style

## Дизайн

GitHub-native, minimal, editorial. Акцент на иерархии, информативности и спокойной плотности информации.

- 1 заголовок H1 на странице, далее H2 и H3 последовательно.
- Обычные отступы между блоками вместо `---`, `***`, `___` и `<hr>`.
- Лаконичное вступление в 1–2 предложения.
- Бейджи только на первом экране README, если они помогают понять проект. Обычно 3–6, максимум 8.
- Нет HTML-таблиц для декоративных колонок, нет искусственного центрирования всего README.
- Нет случайных эмодзи, крупных баннеров, псевдокарточек и emoji-маркеров в заголовках.
- Таблицы для сравнений и параметров. Текст для объяснений, списки для перечислений.
- Mermaid при реальном разветвлении и полезной архитектурной схеме. Не рисовать тривиальные цепочки.
- Заголовки содержательные: `Быстрый запуск`, `Архитектура`, `Настройка окружения` вместо `Всё, что нужно знать`.

## Цветовой код бейджей

Палитра предлагается для утверждения; изменение значений централизовано в этом файле. Цвет выбирают по **смыслу**, а не по настроению автора.

| Категория | HEX | Применение |
| --- | --- | --- |
| Платформы и интеграции | `2563EB` | Telegram, iOS, Android, внешние платформы |
| Языки и runtime | `7C3AED` | Python, Kotlin, Swift, Go, Node.js |
| Фреймворки | `0D9488` | Django, Flutter, SwiftUI, Vue |
| Данные и хранение | `4F46E5` | PostgreSQL, Redis, SQLite, S3 |
| Инфраструктура | `475569` | Docker, Terraform, hosting, deployment |
| Подтверждённый успех | `15803D` | Реально успешная сборка или тест |
| Документация и лицензии | `64748B` | Docs, MIT, Apache |
| Запланировано | `D97706` | Не подключённая пока платформа |
| Ошибка или блокировка | `B91C1C` | Реально неуспешная сборка или blocker |

HEX без `#` в URL Shields.io. Добавлять новые цвета только при необходимости нового семантического статуса.

## Формат Shields.io

Везде `style=flat-square`; `logoColor=white` при наличии светлого логотипа. Ссылку с бейджа направлять к релевантному источнику: workflow, инструкциям, реализации или официальной технологии.

Пример формы, **не готовое утверждение о произвольном проекте**:

```md
![Python](https://img.shields.io/badge/Python-3.12%2B-7C3AED?style=flat-square&logo=python&logoColor=white)
![PostgreSQL](https://img.shields.io/badge/PostgreSQL-16-4F46E5?style=flat-square&logo=postgresql&logoColor=white)
![Docker](https://img.shields.io/badge/Docker-Compose-475569?style=flat-square&logo=docker&logoColor=white)
```

Версии сверять с манифестом проекта. Не путать заявленную поддержку, реализованную интеграцию, тестовое покрытие и успешный продакшен-деплой.

### Статусы

- `passing` – только динамический GitHub Actions/CI badge, связанный с существующим workflow, либо подтверждённая внешняя система.
- `coverage` – только при реальном отчёте покрытия; не вычислять по наличию тестов.
- `release` – только из реальных тегов/релизов.
- `license` – только при наличии корректного лицензирующего файла или явно заданной лицензии.
- `planned` – только если информация о планах действительно помогает. Не украшать первый экран десятком дорожных карт.

## Текст и типографика

Пунктуационное тире – `–` с пробелами; диапазон `1–3` без пробелов; дефис в `Telegram-бот`. Не использовать `—`. Числа цифрами. Технические имена и команды сохраняют исходный синтаксис. Ключевые инструкции не прячутся в `<details>`.

## Предпросмотр

Проверяй README непосредственно в GitHub Markdown или совместимом preview. Убедись, что рендеринг одинаково удобен в светлой и тёмной темах. Внешние SVG и бейджи не должны быть критичны для понимания без изображения.
