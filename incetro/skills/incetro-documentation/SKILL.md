# Incetro documentation

Использовать при первоначальном аудите документации, создании README, изменении продуктовых сценариев, API, конфигурации, архитектуры, деплоя и при проверке PR.

## Входные данные

Изучи текущий репозиторий, README, docs, инструкции агентов, тесты, публичные API, зависимости, пример конфигурации, контейнеры и рабочие скрипты. Если факта нет в источниках, не указывай его как подтверждённый. Не копируй в документы секреты.

## Режим 1 – initial documentation

1. Проведи инвентаризацию существующих документов, оцени актуальность и роли по `living-docs-governance`: правила, карта, статус, история. Используй имеющиеся файлы.
2. Опиши целевые аудитории: разработчик, сопровождающий, оператор, интегратор и пользователь. В маленьком репозитории роли могут объединяться.
3. Выдели подтверждённые сведения: что делает продукт, что ещё не реализовано, как локально запустить, что протестировано, кто зависит от каких компонентов.
4. Обнови или создай README с содержательным первым экраном: название, 1–2 предложения назначения, до 6 проверенных бейджей, особенности, быстрый старт, индекс документации.
5. Добавляй только необходимые тематические документы. Не создавай `docs/api` без реальных API, `docs/operations` без существенной эксплуатации и `docs/architecture` для 1 маленького скрипта.
6. Проверь навигацию и выполнимость команд. Схемы Mermaid составляй по исходному коду; иллюстрации используйте только для реальной пользы.
7. Прогони проверку качества и получи независимый review.

## Режим 2 – continuous documentation

По завершении каждой содержательной задачи ответь на вопросы:

- Изменилось назначение, новая функция или пользовательский сценарий? Обнови каноническое продуктовое описание.
- Изменились компоненты, зависимости, границы, схема данных? Обнови карту архитектуры.
- Изменился запуск, переменная среды, порт, Make target, тест, инструмент? Обнови руководство разработчика и quickstart.
- Изменилось развертывание, резервные копии, мониторинг, восстановление? Обнови эксплуатационное руководство.
- Изменилось внешнее API или формат взаимодействия? Обнови контракт API из источника; при наличии генератора запускай его.
- Решение важно и трудно обратимо? Добавь ADR в уже существующее место.
- Объективно ничего из перечисленного не затронуто? Не изменяй документацию ради отчётности.

Всегда сравни изменения с уже существующим каноническим документом. Не создавай `docs` параллельно проектному Wiki без основания.

## Стандарты

Прочитай `references/visual-style.md` и `references/information-architecture.md`. Ориентир структуры – `templates/README.md`. В шаблоне плейсхолдеры, не публикуй их без замены проверенными фактами.

- Используй нативный GitHub Markdown. Заголовки и пробелы вместо декоративных разделителей.
- Предпочитай 1 канонический источник на факт и ссылки на него из README.
- Бейджи только Shields.io, `style=flat-square`, семантические цвета из утверждаемой палитры.
- Никогда не маркируй `passing`, `production`, `100%` без проверяемого актуального источника.
- Не применяй огромные hero, вёрстку на HTML-таблицах или псевдокарточках.
- Русская типографика по правилу `incetro-copy`.
- Файлы принадлежат проекту. Установщик Incetro ECC их не перезаписывает.

## Проверки

Из корня проекта:

```bash
node .cursor/skills/incetro-documentation/scripts/check-docs.js
```

Скрипт проверяет Markdown-разделители, длинное тире в обычном тексте, Shields.io `flat-square` и существование простых относительных ссылок. Семантику, актуальность, цвета по категориям и корректность команд проверяет агент и тесты проекта. Для GitHub CI смотри `references/ci.md`. Автоматическая установка workflow в проект не производится.

## Выдача

Укажи изменённые документы, источники подтверждения, какие проверки выполнялись и что не проверено. Не утверждай, что вызов `incetro-docs-reviewer` был автоматическим, если отдельная проверка не выполнялась.
